# 🦉 עין הינשוף – מערכת RAG לארכיון סוכנות בילוש

מערכת שאלות ותשובות בשפה טבעית על ארכיון של סוכנות בילוש בדיונית.
המערכת מאתרת את הקטעים הרלוונטיים במסמכי הארכיון, שולחת אותם למודל שפה, ומחזירה תשובה מבוססת יחד עם המקורות שעליהם היא נשענת.

כל המידע במאגר בדיוני, ולכן מודל השפה אינו מכיר אותו מהאימון שלו: תשובה נכונה מוכיחה שהמידע הגיע מהאחזור ולא מהזיכרון של המודל.

---

## מאגר המידע

12 מסמכי Markdown בעברית בתיקייה `data/`, בחמישה סוגים:

| קבצים | סוג | תוכן |
|---|---|---|
| 01 | סקירה כללית | היסטוריה, מחלקות, צוות |
| 02 | תקנון | סעיפים ממוספרים |
| 03, 04 | נהלים | נוהל שמירת מוצגים (שתי גרסאות) |
| 05, 06, 07 | תיקי חקירה | גניבה בנמל, היעלמות כנרת, הרעלה במאפייה |
| 08, 09 | חומרי תיק | דוח מעבדה ותמליל תחקור (תיק ההרעלה) |
| 10 | עלון פנימי | חדשות הסוכנות |
| 11 | אינדקס | טבלת תיקים |
| 12 | מדריך הדרכה | שיטת תחקור |

## ארכיטקטורה

המערכת מחולקת לשני שלבים, בשני קבצים נפרדים:

```
שלב הכנה (פעם אחת) – ingest.py
  data/*.md ─► SimpleDirectoryReader ─► SentenceSplitter ─► Embeddings ─► VectorStoreIndex ─► storage/
              (12 מסמכים)              (59 מקטעים)        (Gemini)

שלב שאלה (בכל שאלה) – app.py
  שאלה ─┬─► חיפוש מדויק למספרי תיקים (regex) ─┐
        └─► חיפוש סמנטי (top_k מקטעים) ──────┴─► איחוד ללא כפילויות ─► Prompt בעברית ─► Gemini ─► תשובה + מקורות
```

**למה שני קבצים:** יצירת ה־embeddings היא החלק האיטי (בקשה ל־Google לכל מקטע) ומוגבלת במכסה. האינדקס נבנה פעם אחת ונשמר לדיסק; בכל שאלה הוא רק נטען, תוך פחות משנייה.

### הקבצים

| קובץ | תפקיד |
|---|---|
| `ingest.py` | טעינת המסמכים, חלוקה למקטעים, יצירת embeddings ושמירת האינדקס ל־`storage/` |
| `app.py` | ממשק Streamlit: אחזור, ניסוח תשובה, הצגת מקורות והיסטוריית שאלות |
| `test_gemini.py` | בדיקת חיבור בסיסית ל־Gemini (מפתח, רשת, התקנה) |
| `problems_log.md` | יומן הבעיות שהתגלו בבדיקות, הניתוח והתיקונים |

## בחירות טכנולוגיות

| רכיב | בחירה | נימוק |
|---|---|---|
| ספריית RAG | LlamaIndex | דרישת התרגיל |
| מודל Embeddings | `gemini-embedding-001` | תומך בעברית ובשליחה במנות (batch). המודל החדש `gemini-embedding-2` החזיר וקטור אחד בלבד לרשימה של 20 טקסטים, ולכן לא נבחר |
| מודל שפה | `gemini-3.5-flash-lite` | מהיר. במהלך העבודה הוחלף מ־`gemini-3.5-flash` בגלל מכסה יומית של 20 בקשות לכל מודל בחשבון החינמי |
| Vector Store | המאגר המובנה של LlamaIndex, שמור כקבצי JSON | 59 מקטעים בלבד: חיפוש בזיכרון לוקח אלפיות שנייה, ואין צורך בהתקנה נוספת. במאגר של אלפי מסמכים הייתי בוחרת ב־Chroma או ב־Qdrant |
| חלוקה למקטעים | `SentenceSplitter`, 512 טוקנים, חפיפה 50 | נקודת התחלה פשוטה וצפויה לפי המלצת החוברת. נבדקה גם חלוקה לפי כותרות (`MarkdownNodeParser`): 76 מקטעים בגדלים של 16 עד 3,632 טוקנים, לא אחיד מדי |
| top_k | 3 (ניתן לשינוי בסליידר) | כ־1,500 טוקנים לשאלה: מהיר ומספיק לשאלה רגילה |
| ממשק | Streamlit | שני כפתורים: "חפש" (אחזור בלבד, לא צורך את מכסת מודל השפה) ו"ענה" |

## התקנה והרצה

**דרישות:** Python 3.11 ומעלה (נבדק על 3.13), ומפתח API של Gemini מ־[Google AI Studio](https://aistudio.google.com/apikey).

1. יצירת סביבה וירטואלית והפעלתה:
   ```
   python -m venv venv
   venv\Scripts\activate
   ```
2. התקנת החבילות:
   ```
   pip install -r requirements.txt
   ```
3. יצירת קובץ `.env` בתיקייה הראשית, עם השורה:
   ```
   GOOGLE_API_KEY=המפתח_שלכם
   ```
4. בניית האינדקס (פעם אחת, כ־15 שניות):
   ```
   python ingest.py
   ```
   בחשבון חינמי יש מגבלה של 100 embeddings בדקה. אם מתקבלת שגיאה 429, יש לחכות דקה ולהריץ שוב.
5. הפעלת הממשק:
   ```
   streamlit run app.py
   ```
   הממשק נפתח בדפדפן בכתובת `http://localhost:8501`.

**הערה לגבי סינון אינטרנט (כמו NetFree):** סינון כזה מחליף את תעודות האבטחה, ו־Python 3.13 דוחה את התעודה שלו. החבילה `truststore`, שמופעלת בראש כל קובץ, גורמת ל־Python לבדוק תעודות דרך Windows ופותרת את הבעיה.

## סיכום: בעיות שנתקלתי בהן ואיך שיפרתי

הפירוט המלא, כולל כל שאלות הבדיקה והתוצאות שלהן, נמצא ב־[problems_log.md](problems_log.md).

### בעיה 1: החיפוש הסמנטי לא מבחין בין מזהים דומים ✅ תוקן

**מה קרה:** לשאלה "מי הבלש האחראי על תיק 2024-017?" המערכת ענתה שאין מידע על התיק, אף שהוא מופיע באינדקס התיקים. נשלפו במקומו תיקים 2024-117 ו־2024-171 – אותן ספרות בסדר אחר.

**הסיבה:** embedding מייצג משמעות ולא רצף תווים מדויק. מבחינת המודל, שלושת המספרים הם כמעט אותו דבר: "מספר תיק משנת 2024". בנוסף, לשני התיקים האחרים יש קבצים שלמים על חקירה, ואילו 2024-017 מופיע רק כשורה בטבלה.

**מה ניסיתי:** חיפוש מילות מפתח (BM25) – הקטע הנכון הגיע רק למקום 4, כי מילים עבריות עם תחיליות ("הבלש", "האחראי") ומילים נפוצות מחלישות את ההתאמה.

**התיקון:** לפני החיפוש הסמנטי, המערכת מזהה מספרי תיקים בשאלה בעזרת ביטוי רגולרי (`\d{4}-\d{3}`), מחפשת את הרצף המדויק בכל המקטעים, ומוסיפה את המקטעים שנמצאו בראש הרשימה. לשם כך פירקתי את ה־query engine לשני חלקיו: אחזור (פונקציה משלי) וניסוח (response synthesizer).

**התוצאה:** הקטע הנכון במקום הראשון, והתשובה נכונה ("איתן בן-חיים").

**מגבלה:** התיקון מכסה רק מזהים בפורמט של מספר תיק.

### בעיה 2: המודל הפך "לא כתוב" ל"לא קיים", וניסח מסקנות שאינן בחומר ✅ תוקן

**מה קרה:** בבדיקה של 8 שאלות "פיתוי" (שאלות שנשמעות קשורות אבל התשובה אינה בחומר), המודל עמד ברוב המקרים, אבל בשניים נכשל חלקית:
- "האם לסוכנות יש סניף בתל אביב?" ← "**לא.** ...ולא מצוין כי יש לה סניף". החומר לא אומר שאין סניף, רק לא מזכיר סניף.
- "האם דורית שמש אשמה?" ← "ראיות **הקושרות** אותה למקום **ולמעשה**, אך אינו קובע את אשמתה **המשפטית**" – ניסוח שהופך חשד למסקנה.

**הסיבה:** ה־prompt של ברירת המחדל (באנגלית) אומר רק "ענה לפי המידע". כשהמודל מקבל ראיות חלקיות, הוא נוטה "להשלים" אותן למסקנה.

**התיקון:** prompt בעברית עם 5 כללים מפורשים: נוסח קבוע ל"אין מידע", הבחנה בין "לא מוזכר" ל"לא קיים", איסור לקבוע אשמה או מסקנה שלא כתובה במפורש, ציון שם הקובץ, ותשובה קצרה (חיסכון בטוקנים).

**התוצאה:** "לא נמצא מידע על כך במאגר", ו"אין בחומר מסקנה רשמית לגבי אשמתה..." עם הצגת הראיות כעובדות. בדיקת רגרסיה על שאלה שעבדה קודם (2024-017) עברה.

**לקחים מהדרך:**
- בהרצה הראשונה שכחתי להעביר את ה־prompt ל־synthesizer, ובכל זאת התשובה השתפרה – במקרה. לא מסיקים ש"תיקון עבד" מתשובה אחת בלי לוודא שהשינוי פעיל.
- כלל "ציין את שם הקובץ" גרם בתחילה להצגת **הנתיב המלא** במחשב. תוקן על ידי דוגמה מפורשת בתוך ה־prompt.

### בעיה 3: מידע שמפוזר על פני כמה מסמכים, ושורת טבלה שנחתכה 📝 זוהתה ונותחה

**מה קרה:** בשאלה על דורית שמש, התשובה האמיתית (סתירה בגרסתה) בנויה מ־5 פרטים ב־3 קבצים: טביעת האצבע נמצאה **בצד הפנימי של המכסה**; צד זה נחשף רק אחרי הסרת החותם; הצנצנת הגיעה כחודש אחרי פיטוריה ונפתחה ב־8.2 בשעה 19:00; רכב לבן קטן נראה ליד המאפייה בלילה; ולדבריה הייתה בבית לבד ויש לה פיאט לבנה. עם top_k=3 המודל קיבל רק פרט אחד מתוך החמישה, ולכן לא ראה את הסתירה.

**הסיבות (שתיים):**
1. **אחזור לפי דמיון לשאלה:** השאלה "האם היא אשמה?" לא דומה סמנטית למשפטים "בבית, כל הערב" או "פיאט קטנה, לבנה". גם עם top_k=8 שני פרטים קריטיים לא נשלפו – הגדלת top_k לבדה אינה פתרון, ומוסיפה רעש וטוקנים.
2. **חיתוך שורת טבלה:** בדוח המעבדה, השורה של מוצג מ-312 נחתכה בין שני מקטעים. המקטע שנשלף מתחיל ב"נמצאו 12 נקודות התאמה...", בלי החלק "בצדו הפנימי של המכסה" – בדיוק הפרט שהופך את הטביעה לראיה. `SentenceSplitter` סופר טוקנים ואינו מכיר מבנה של טבלה.

**פתרונות אפשריים (לא מומשו בגלל מגבלת המכסה):**
- פירוק השאלה לתת־שאלות (`SubQuestionQueryEngine`): "איפה נמצאה הטביעה?", "מתי נפתחה הצנצנת?", "איפה דורית טוענת שהייתה?" – כל אחת נשלפת בנפרד. המחיר: כמה קריאות למודל בכל שאלה.
- חלוקה מודעת־מבנה (קודם לפי כותרות, ואז לפי גודל), כך ששורות טבלה לא יתנתקו מהכותרת שלהן.

**התובנה:** ה־prompt משפר את *הניסוח*, אבל לא את *מה שנשלף*. אם הקטע הנכון לא הגיע למודל, שום הוראה לא תעזור – בדיוק כפי שהחוברת מזהירה בפרק 9.

## רעיונות להמשך

- פירוק שאלות מורכבות (Decomposition) לשיפור שאלות שהתשובה עליהן מפוזרת בכמה מסמכים.
- חלוקה מודעת־מבנה והשוואה מדודה מול `SentenceSplitter`.
- עדכון הדרגתי של האינדקס: embeddings מחדש רק לקבצים שהשתנו (לפי `last_modified_date`).
- קובץ הגדרות משותף ל־`ingest.py` ול־`app.py`, כך ששם מודל ה־embeddings יוגדר במקום אחד בלבד.
- הרחבת החיפוש המדויק לסוגי מזהים נוספים (מספרי סעיפים, קודי מוצגים).
